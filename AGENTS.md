# Pulse CMS engineering rules

Work incrementally in the existing Laravel application under `cms/`; never replace it with a new installation. Preserve working behavior, but repair insecure or unmaintainable code. Keep HTTP, validation, authorization, application, domain, persistence, integration, presentation, queue, configuration, audit, and observability concerns separated. Prefer Form Requests, policies/gates, actions, contracts/adapters, events/jobs, enums/value objects, and explicit dependencies; prohibit business logic in routes or Blade, direct `env()` outside config, unbounded large queries, floating-point money, debugging artifacts, and placeholder functionality.

Treat input as hostile and authorization as deny-by-default. Protect every administrative capability at the backend as well as in UI. Never commit/log/re-display secrets; validate uploads, webhooks, redirects, paths, and provider responses. Record security-sensitive and financial actions. Target WCAG 2.2 AA and use reusable Pulse components rather than browser alerts.

Before each milestone: inspect applicable instructions and current state. After it: inspect the diff, remove accidental/dead files, run relevant checks, update docs and `NEXT.md`, then make a focused commit and push without rewriting history. Do not change a valid Git identity or add AI attribution. Never claim an unrun test passed. Record unavoidable debt in the debt register, not TODO/FIXME comments.

Required baseline commands (from `cms/`): `composer validate --strict`, `vendor/bin/pint --test`, `php artisan test`, `php artisan route:list`, `npm run build`, and an application smoke test. Run narrower tests during development, then all available gates before release. Environment limitations must be reported accurately.

Canonical detail: [scope](docs/product/PRODUCT_SCOPE.md), [contract](docs/engineering/ENGINEERING_CONTRACT.md), [current architecture](docs/architecture/CURRENT_STATE.md), [target architecture](docs/architecture/TARGET_ARCHITECTURE.md), [security](docs/security/SECURITY_REQUIREMENTS.md), [testing](docs/testing/TEST_STRATEGY.md), [audit](docs/audits/INITIAL_CODEBASE_AUDIT.md), [debt](docs/audits/TECHNICAL_DEBT_REGISTER.md), [roadmap](ROADMAP.md), and [recovery state](NEXT.md). Keep documentation factual; planned behavior must be labelled planned. Use `docs/adr/` for consequential decisions. Migrations are canonical; validated release SQL belongs in `database/releases/` only at release readiness.
