# Current state

Audit date: 2026-07-30. This describes observed code, not intended behavior.

The repository contains a Laravel 13 / PHP 8.3 application in `cms/`, with Blade-rendered admin/public interfaces and directly served CSS/JavaScript. Eloquent models and migrations exist for users, settings, pages, media, blog taxonomy/posts, menus, themes/settings, and plugins/settings. Controllers and routes provide basic CRUD, builder, theme, plugin, SEO and settings screens. Plugin behavior is currently a small manager/helper rather than a complete isolated runtime.

Authentication provides a custom throttled admin login/logout flow with session regeneration and disabled-account enforcement. Signed/throttled email verification gates administrative capabilities; password recovery is non-enumerating and restricted to active accounts; credential and session changes require password confirmation; profile email changes require reverification; and database-backed sessions are visible and revocable only by their owner. These identity security events are audited. Normalized roles, permissions, pivots, canonical permission enum, system-role migration, Gate integration, per-route enforcement, permission-aware navigation, and initial authorization matrix tests are implemented. The legacy `users.role` column remains temporarily for compatibility. User and custom-role administration use validated, permission-protected workflows with safe delegation, immutable system roles, final-active-super-administrator safeguards, pagination, and append-only audit records. Permission-bearing users must complete standards-based TOTP MFA before privileged routes; encrypted secrets, hashed single-use recovery codes, replay protection, challenge throttling, session regeneration, and audited recovery/reset operations support that boundary. The expanded identity authorization matrix is implemented.

The administration UI now has a documented three-layer CSS token architecture, local Vite assets, permission-aware responsive shell, reusable Blade foundations, safe toast live region, and accessible confirmation dialog. All registered administration views now use the Pulse component and `p-*` presentation contracts; media, menus, builder, themes/customizer, plugins/settings, site settings, and SEO completed the final M2 conversion. All administration destructive actions use the custom dialog. Browser and assistive-technology inspection remains outstanding.

Builder V4 stores schema-v1 documents with stable UUID nodes, a closed server registry, bounded container nesting and responsive tokens. Focused requests and an atomic action extend Page optimistic locking; persisted reusable templates insert as independent snapshots. Public and signed private preview rendering share a fail-closed validated resolver and managed media references. Legacy unversioned data remains recoverable in storage but is not rendered or automatically rewritten. Themes remain database records/settings rather than three fully packaged first-party themes. Commerce, gateway adapters, webhook ledger, notifications, secure installer, protected log viewer, and release SQL are absent.

The test suite includes authentication, authorization, user/role administration, and identity lifecycle feature coverage in addition to framework examples. Locked dependencies can be restored with Composer; a local `.env` is not committed. The Git branch is `work`; configured identity exists; no remote is configured.

M3 page/post lifecycle hardening now centralizes four lifecycle states and validation, public eligibility, conditional scheduled publication, signed private previews, slug rules, transactional mutations, audit events, and optimistic locking. Page hierarchy and media foreign-key conversion are not present in the inherited schema; builder schema/revision history remains assigned to M4.

Taxonomy now uses separate category and tag URL namespaces. Names are trimmed, whitespace-collapsed, Unicode-normalized, case-folded into a database-unique comparison value, and limited to 100 characters; ASCII slugs are lower-kebab normalized, reserved values are rejected, and remain database-unique per taxonomy type. Categories are deliberately flat. Assignments require `taxonomy.manage`, accept at most 50 distinct valid tags, and are synchronized inside the content transaction. Taxonomies with assigned posts cannot be deleted. Administration is usage-aware and paginated; public archives use the shared post visibility scope, eager loading, deterministic ordering, and pagination.

## M3 media follow-up

Media administration now accepts only bounded, successfully decoded JPEG, PNG, WebP, and GIF images; uses opaque public-disk paths; derives MIME and dimensions; paginates records; supports audited metadata changes; and blocks deletion while pages or posts reference an asset. Pages and posts use nullable restrictive media foreign keys and bounded editor choices. The former post URL column is retained as inactive `legacy_featured_image` data so deployment-specific URLs are not silently discarded or fabricated into managed records.

Menu mutations now use focused requests and transactional actions. Main and footer activation is unambiguous, item operations are parent scoped, flat ordering is normalized atomically, page links derive from current slugs, and public navigation excludes page content outside the shared publication scope. Page deletion is restricted while navigation references exist.


## M3 SEO

SEO settings now use an explicit request and transactional action rather than arbitrary setting-key persistence. `seo.manage` independently protects global and per-content metadata. Public rendering receives a resolved SEO document with same-origin canonical overrides, context-aware Open Graph/Twitter and safely encoded WebSite/WebPage/BlogPosting data. Global social images are managed-media references protected from deletion. Robots output is normalized and sitemap output is cached with explicit content/taxonomy/SEO invalidation, lazy bounded queries, 50,000-URL enforcement, real modification timestamps, homepage deduplication, and public category/tag archives.

## Forms

First-party forms use normalized unique slugs, explicit active state, a closed ten-type field schema, bounded ordered fields, compiled trusted validation, and immutable submission snapshots. Public POSTs are CSRF and rate-limit protected and reject unknown keys. Administration and submission access require `forms.manage`, verified active identity, and privileged MFA; submission contents are never audited.
